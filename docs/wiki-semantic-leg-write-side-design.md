## 0. 一句话结论（分两层，不要合并读）

**可行性：成立** —— 而且**代码里已经有现成先例**：词法投影（`wiki_body_fts` / `wiki_body_projection`）
早就是「按 `content_hash` 去重、写入期算一次」的形态。语义腿缺的**不是新架构，是没走这条既有路子**。

**时机：尚不成立** —— 语义腿今天**没有任何生产调用者**（决定性证据见 §1.3），
所以 O(全代页×块)/查询 的成本是**潜在的，不是现实的**。

⇒ **建议：记录设计与触发条件，暂不实现。** 一旦有人把 `semantic_embedder` 接进生产路径，本提案的设计即可直接采用。

## 0.1 两条硬约束（不可协商，先于所有选项）

### 约束 A：只允许 local transport 嵌入器；拿不到就降级纯 bm25，**绝不把 wiki 正文发往远端**

`retrieval_factory.py:49-58` 的既有口径：本地为默认，远端**需用户显式配置 key**（opt-in），
且本地隐私模式下**配置了远端 key 也会被忽略**，理由是原注释所写「remote transport would leak private text」。

⇒ **陷阱**：检索用的向量索引可以是**远端**的（`:86` `transport = _TRANSPORT_REMOTE`；`:98-103` 远端分支）。
所以**写入侧绝不能直接复用 `build_vector_index()` 解析出的嵌入器** —— 那会把 wiki 正文发往远端。
写入侧必须**独立解析一个仅本地**的嵌入器（等价于 `_TRANSPORT_LOCAL` 分支 / `build_local_onnx_embeddings`），
拿不到就**一条向量都不写**，语义腿自然回落到纯 bm25（`snapshot_reader.py:203` 的 `is not None` 判据天然支持）。

### 约束 B：向量只是**排序输入**，绝不是权威来源；**撤销页不得因预计算/缓存而被复活**

既有机制：语义排名内先过逐页授权闸（`snapshot_reader.py:283-285`），
且 `search()` 末尾仍对每条候选做 `_load` 逐条复核（`:322-323` 注释明写「权威闸仍由下方 search() 末尾的逐条 _load 复核」）。
既有测试已钉死该保证：`test_wiki_semantic_fusion.py:124-137`
`test_semantic_channel_cannot_resurrect_a_revoked_page`。

⇒ **预计算不改变这条边界**：向量表只能喂排序，**不得**成为任何「这页存在/可读」的依据。
撤销的判定仍必须来自候选复核那一刻的权威检查，**不能来自向量是否存在**。
**这一条是选项 1 是否安全的关键，必须在测试里显式扩展覆盖（§5）。**

## 1. 现状（带行号）

### 1.1 成本中心在读侧，且是 O(全代页 × 每页块数) **每次查询**

`snapshot_reader.py:268-317` `_semantic_page_ranking_inner`：

| 行 | 动作 | 复杂度 |
| --- | --- | --- |
| `:273-279` | `SELECT … FROM wiki_generation_pages JOIN wiki_page_bodies` —— 读**本代全部页正文** | O(页) |
| `:286-288` | 对每页 `parse_markdown` 分块 | O(页) |
| `:299-300` | `embed_query(query)` + **`embed_documents(flat)`（flat = 全代所有块）** | **O(页×块) 次嵌入** |
| `:306-315` | 全块余弦 + 页内最佳块聚合 | O(页×块) |

⇒ 每次检索都要把**整代 wiki 正文重新嵌入一遍**。页数增长时线性劣化。
这正是 engineer-rrf 判定「on-the-fly 嵌入生产不可行」的那一处。

### 1.2 词法投影**已经**做了「按 content_hash 去重、写入期摊销」——语义腿没有

`projections.py:20` `build_generation_projection`：
- `:32-34` 先查 `SELECT * FROM wiki_body_projection WHERE vault_id=? AND content_hash=?`；
- `:35` `if projected is None:` —— **只有没算过的正文才** `parse_markdown` + 写 `wiki_body_fts` / `wiki_body_projection`；
- `:51-52` 命中则直接复用。

⇒ **同一份正文在任意多代之间只算一次**。这是现成的、已验证的摊销模式。
语义腿要做的事，本质是**把向量投影补成同一形态的第三张投影表**。

调用点：`generations.py:127-129`（**stage 时**构建）、`publication.py:332/368`（**promote 时**再构建/校验）。
即**写入期已经有一个天然的钩子**，且它允许写共享投影（`wiki_body_fts` 就是共享的）。

表结构先例：`migrations/033_wiki_snapshot_projections.sql:1-19`
（`wiki_body_projection` 以 `(vault_id, content_hash)` 为主键并外键指向 `wiki_page_bodies`；
`wiki_body_fts` 以 `(vault_id, content_hash, chunk_index)` 为块级键）。

### 1.3 **决定性事实：语义腿今天没有生产调用者**

`semantic_embedder` 是 `snapshot_reader.py:90` 的构造参数，默认 `None`。
**全仓检索该参数，除 `snapshot_reader.py` 自身外只有 3 处，且全部是测试/评测**：

```
apps/backend/tests/phase_d_fusion_ablation.py:115
apps/backend/tests/phase_d_eval.py:138/150
apps/backend/tests/test_wiki_semantic_fusion.py:63
```

**生产构造点 `app/api/services/factory.py:552` 是 `WikiSnapshotReader(db, wiki, authorize=authorize)` —— 不传嵌入器。**
⇒ 生产路径上 `semantic_embedder is None` ⇒ `:203` 分支不进入 ⇒ **语义腿恒为关闭，走纯 bm25**。

**所以 §1.1 的 O(页×块)/查询 成本目前不在任何生产路径上发生。**

### 1.4 向量腿与词法腿的 join 形态（选项 1 直接沿用）

`snapshot_reader.py:172-175` 词法腿的 join：
```
FROM wiki_body_fts JOIN wiki_generation_pages p
ON p.vault_id = wiki_body_fts.vault_id AND p.content_hash = wiki_body_fts.content_hash
```
向量投影按同一形态 join 即可：**代决定「有哪些页」，content_hash 决定「算没算过」**。

## 2. 选项

### 选项 1（设计推荐）：新增 content_hash 键的向量投影表，在写入期构建

**落点**：`build_generation_projection`（`projections.py:20`）内，与 `wiki_body_fts` 并列新增一张投影表。

**表形态（沿用 033 的形状，不新造范式）**：
```sql
CREATE TABLE wiki_body_vectors (
    vault_id TEXT NOT NULL,
    content_hash TEXT NOT NULL,
    chunk_index INTEGER NOT NULL,
    model_id TEXT NOT NULL,      -- 身份:模型/维度变了必须失效,不能静默复用
    dims INTEGER NOT NULL,
    vector BLOB NOT NULL,        -- float32 打包
    PRIMARY KEY(vault_id, content_hash, chunk_index, model_id),
    FOREIGN KEY(vault_id, content_hash) REFERENCES wiki_page_bodies(vault_id, content_hash)
);
```

| 维度 | 内容 |
| --- | --- |
| 改动性质 | **新增数据通路**（新迁移 + 写路径 + 读路径），但**复用既有摊销范式**，不是新架构 |
| 成本变化 | 写：O(新增/变更正文)；读：**O(1) 次嵌入**（只嵌 query）+ O(页×块) 次点积 |
| 能实现 | 语义腿在生产可负担；跨代去重（同一正文只算一次） |
| **不能实现** | **不改变覆盖完整性**（见下「覆盖偏斜」） |
| 风险/回归面 | 新迁移；`build_generation_projection` 是 stage/promote 的**关键路径**，写失败会影响发布；需处理嵌入器不可用 |
| 可验证性 | 见 §5 |

**必须声明的真实代价 —— 覆盖偏斜（这是本选项最该被反对的点）**：
写入期向量**只在写入那一刻嵌入器可用时**才存在。若某页发布时本地 ONNX 不可用，
该页**永久没有向量**（直到重新发布），而它的同类页有 —— 于是**它对自己的语义召回不可见，对别人的可见**。
查询期嵌入不存在这个问题（每次都在同一条件下覆盖全集）。
⇒ **两种缓解，必须二选一并在实现时明确**：
1. **全代原子**：本代任一页缺向量 ⇒ 整代不启用语义腿（回到纯 bm25）。**简单、无偏斜、但可用性变差**；
2. **补算/修复通道**：缺向量的页由后台补齐，补齐前该代语义腿标记为不完整。**复杂、但可用性好**。
**不选任何一条就等于默认接受静默偏斜** —— 那会让「融合优于单路」的评估结论不可信。

### 选项 2：进程内 LRU 向量缓存（读侧缓存，**不落库**）

**做法**：`_semantic_page_ranking_inner` 把 `embed_documents(flat)` 的结果按 `(content_hash, chunk_index, model_id)` 缓存进进程内 LRU；命中则跳过嵌入。

| 维度 | 内容 |
| --- | --- |
| 改动性质 | **补逻辑**（无迁移、无写路径） |
| 成本变化 | 首次查询仍 O(页×块)；**之后**每查询 O(1) 嵌入 |
| 能实现 | 稳态成本；**无覆盖偏斜**（覆盖条件每次一致） |
| **不能实现** | **冷启动成本**：进程重启/首次查询仍全量嵌入；多进程各自付一遍 |
| 风险/回归面 | 低。纯读侧、纯内存、可随时清空；不新增持久状态 |
| 可验证性 | 可测「第二次查询不再调用 `embed_documents`」（计数桩） |

**它比选项 1 差在哪**：不解决冷启动，且缓存随进程消失 —— 对「Electron 桌面端反复启停」的场景收益有限。
**它比选项 1 好在哪**：**没有覆盖偏斜**，且**成本低一个数量级**（无迁移、无写路径风险）。

### 选项 3：**不做**（时机选项，**不是**设计替代）

**这不是凑数**，它有一条明确证据与一个明确触发条件：

- **证据**：§1.3 —— 语义腿**零生产调用者**，成本是潜在的。为一个没有调用者的能力新建迁移 + 改 stage/promote 关键路径，
  属于「为未证实需求建组件」；本会话已按同一把尺子**拒绝过** RRF 融合与 t9 的选项 D。
- **触发条件（何时改判）**：**一旦有人把 `semantic_embedder` 接进生产路径**（例如 wiki 查询节点开始注入它），
  §1.1 的成本立刻变为现实，**此时选项 1 的设计即可直接采用**。

| 维度 | 内容 |
| --- | --- |
| 改动性质 | 无 |
| 能实现 | 不引入任何新风险 |
| **不能实现** | 语义腿一旦上线仍会全量嵌入（但今天不上线） |
| 可验证性 | 「无生产调用者」本身可被 §1.3 的 grep 复核，是可证伪的 |

## 3. 推荐

**推荐：选项 3（暂不实现），并预置选项 1 的设计。**

**一句话理由**：可行性已证明（§1.2 的既有范式），但**成本今天不发生**（§1.3 零生产调用者）——
**在有调用者之前建写入侧基础设施，就是为未证实需求建组件。**

**为什么其它选项更差**：
- **选项 1 更差（现在做）**：新迁移 + 改 stage/promote 关键路径 + 引入**覆盖偏斜**这一新失效模式，
  换来的收益在**当前没有任何调用者**的前提下等于零。
- **选项 2 更差（作为长期方案）**：不解决冷启动、不持久化；但它**比选项 1 更适合作为「接线后的第一步」**——
  成本低、无偏斜、可随时撤。

**若 captain 决定接线语义腿，建议顺序**：先选项 2（低成本、无偏斜）→ 用评测量出稳态收益 → 若冷启动确实成为问题，再上选项 1。
**这个顺序与 t9 的执行顺序逻辑一致：先拿到能判断下一步的证据，再建重资产。**

## 5. 可验证性（不接受「看起来对」）

| 选项 | 能证明什么 | 用什么证明 | **不能证明什么** |
| --- | --- | --- | --- |
| 1 | ①写入期按 content_hash 去重（同正文跨代只算一次）；②读侧每查询只嵌 1 次（query）；③**撤销页仍不复活**；④嵌入器不可用时**不写向量且语义腿回落 bm25** | 计数桩嵌入器断言调用次数；跨代复用断言；**扩展 `test_semantic_channel_cannot_resurrect_a_revoked_page` 到「预计算向量存在」前提**；本地嵌入器不可用注入 | 真实收益（需评测）；覆盖偏斜概率 |

**约束 A 的验证（独立于选项）**：注入一个「远端」嵌入器替身，断言写入侧**拒绝使用它且不写任何向量**。
